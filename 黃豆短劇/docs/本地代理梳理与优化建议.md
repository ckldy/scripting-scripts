# 本地代理梳理与优化建议（2026-08-07）

> 基于 proxy.ts(586 行) / proxy_main.ts / client.ts(294 行) / index.tsx / episode-player.tsx / native-player.tsx 全文审阅。

## 一、当前架构

```
启动：proxy_main.ts（常驻） 或 index.tsx（startProxyServer → /ping 健康检查 5×500ms）
      └─ HttpServer :8787（forceIPv4，setNotFoundHandler 全量接管）

处理链（/api/* 请求）：
  客户端加密请求 ──解密(requestId→key)──▶ 代理自建请求（新 requestId/sign/加密 body）
      ──8 线路循环容错（preferredLineBase 优先）──▶ 上游 ──解密──▶ 改写
      ├─ /user/info    → 钻石会员 + 999999 金币视图（本地扣费 38/集）
      ├─ /drama/play   → 付费墙(813005/813004) → 金币直连 m3u8（免费直取，已验证无鉴权）
      │                  preferredLineBase 已确认时走「快速预取」：不等上游验证直接构造直连地址
      ├─ /drama/doBuy  → 上游失败 → 改写成功 + 视图扣费
      ├─ /user/doSign  → 上游失败 → 改写成功（VIP 1天视图）
      ├─ /drama/detail → 付费集全部 is_buy=true
      └─ 其余透传
      ──客户端 key 重加密──▶ 返回

播放链（HLS）：
  AVPlayer → http://127.0.0.1:8787/hls/{url}（或 /cdn/{url}，encodeURIComponent 原URL）
      ──Safari UA 拉上游（绕开 CloudFront 对 AppleCoreMedia UA 的挂起）──▶
      m3u8：改写 key/分片 → /cdn/；master playlist 自动选最高码率变体；
            线路回退（记忆缓存 → 首选 4s 探测 → 最多 3 条备用线路各 4s）
      key/分片：3 次重试 × 30s 全包超时；6h/短时缓存 + hlsInFlight 去重
      后台预热（key + 首片，waitForWarm 串行版供连播页 X-Huangdou-Warm 使用）
```

健康闭环：代理自持「解锁身份」（独立 deviceId，每日签到拿 VIP 1 天）+ 客户端「视图状态」（钻石会员+金币模拟），全部持久化。

## 二、可以优化的点（按优先级）

### P0 — 行为问题

1. **端口被占时 index.tsx 直接退出，不尝试复用已有代理**
   - 现状：先跑 proxy_main.ts 常驻 → 再开 index.tsx → `server.start` 返回 error → 抛「代理启动失败」→ 退出提示。
   - 但此时旧实例明明还在 8787 上服务，客户端本来就只连 127.0.0.1:8787，完全可以直接用。
   - 建议：`startProxyServer` 里 start 失败时先 `fetch("http://127.0.0.1:8787/ping")`，通了就视为"已就绪"返回（并让 index.tsx 不再退出）；不通才抛错。
   - 收益：消除最常见的双启动冲突；风险极低（ping 已有）。

### P1 — 可靠性 / 内存

2. **m3u8 线路回退只匹配 `?line=free` 格式**
   - 现状：`fetchManifestWithLineFallback` 的正则 `...play\.m3u8\?line=free$` 只对金币直连 URL 生效；真实解锁身份拿到的 m3u8（或 preview_m3u8、其他 query）线路挂了时无兜底 → 播放失败。
   - 建议：放宽为任意 `play.m3u8`（query 任意），回退候选统一构造已验证可用的 `?line=free` 直连格式（`/api/drama/hls/{id}/{seq}/play.m3u8?line=free` 无鉴权 HTTP 200 已实证）。
   - 收益：更多剧集获得线路容错；风险低（fallback 是"多一层兜底"，失败仍回退原结果）。

3. **hlsCache 无定期清理（Map 无限增长）**
   - 现状：只有命中过期 key 时 delete；长时间看剧（每集几十片 × 10min TTL）会累积大量 Uint8Array 不释放。
   - 建议：启动时 `setInterval` 每 5 分钟扫一遍删除过期项（或加条目上限如 300）。
   - 收益：长会话内存稳定；风险极低。

4. **preferredLineBase / hlsLineCache 不持久化**
   - 现状：内存态，代理重启后首播又得重新探测（最多 4s+）。
   - 建议：持久化到 Storage（如 `huangdou_proxy_line_v1`），启动加载、变更写回。
   - 收益：重启后首播/首请求提速；风险低。

### P2 — 代码清理（减负）

5. **client.ts 真实线路是死代码**
   - 现状：`request` / `ensureLogin` 都是 `for (const index of [0])`，API_LINES 后 8 条真实线路永远不可达；`activeLine` 只赋值从不读取。
   - 建议：删除真实线路数组与 activeLine，rawRequest 不再传 line（base 恒为 local 常量）。
   - 收益：client.ts 减 ~30 行、消除误导（注释还写着"自动回退真实线路"与强制代理矛盾）；风险低（接口不变，测试引用的是方法不是线路表）。

6. **native-player.tsx + media-player/ 是死代码（需确认删除）**
   - 现状：`presentDramaPlayer` 无任何调用方（主路径是 detail.tsx → episode-player.tsx → AVPlayer）；hls.js 兜底在真机已被验证不可用（记忆：window.play 未定义，勿回该路线）。
   - 建议：删除 native-player.tsx、media-player/hls-player-service.ts(1200 行)、hls.min.js(414KB)，保留 test_* 可一并清理。
   - 收益：项目瘦身 ~1.6MB 且消除"错误的兜底"；需用户确认（属删除功能）。

7. **proxy.ts 内部重复：unlockRequest 与 handleProxy 上游转发逻辑几乎相同**
   - 建议：提取 `forwardToUpstream(path, data, {token, deviceId})` 公共函数（线路循环/加密/sign/fetch/解密），unlock 与主链共用。
   - 收益：-40 行左右、单一维护点；风险中（主链改动需回归 test_coin_direct/test_proxy_ts）。

8. **proxy.ts 与 client.ts 协议工具重复**（deriveKey/dataFromHex/hex/isCompressed/withTimeout 各一份）
   - 建议：抽 `protocol.ts` 共享；收益维护性，风险中（改 client 需回归 test_full 等），可放最后做。

### P3 — 微小

9. `/hls/` 与 `/cdn/` 分支相同：`req.path.startsWith("/cdn/") ? slice(5) : slice(5)` → 直接 `slice(5)`。
10. doBuy/play 扣费 `38` 硬编码 → 提取 `COIN_PRICE = 38` 常量并注释平台规则。
11. 日志噪音：每请求/每分片都 console.log，可加 `DEBUG` 开关（默认开，正式用关）。
12. detail.tsx 的 play() 外层 resetIdentity 重试与 client.play 内部状态机重叠（双保险但历史遗留），可评估收敛。

## 三、不建议动（已确认设计）

- 加解密链路、sign 重算、/api 前缀、节点 fetch 限制：均为平台硬约束，保持现状。
- 分片预取：签名 1h 有效期 + AVPlayer 顺序拉取 + 缓存/inFlight 已足够，无收益。
- fast path（/drama/play 快速响应 + 后台预取）：当前设计合理，配合 P1-4 持久化后首播也能快。

## 四、建议实施顺序

1. P0-1 端口复用（小改，立即收益）
2. P1-2/3/4（可靠性+内存，均小改）
3. P2-5（client 死代码清理，配 test_full 回归）
4. P2-7（proxy 提取公共转发，配 test_coin_direct/test_proxy_ts 回归）
5. P2-6（native-player/media-player 删除，需用户确认）
6. P3 与 P2-8 视需要收尾
